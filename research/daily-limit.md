## 1. 【问题 1】每日任务点上限是否真实存在

### 1.1 三条独立来源都指向"存在"

**① 平台 DOM 里的隐藏提示框（最硬的一条）**

- **B｜实测记录**：`sansssssss1/auto-online-course-agent-skill` → `knowledge/chaoxing.md` §8：
  > 隐藏提示框 class `maskDiv jobCountDiv`：「今日视频任务点完成数已达上限，您可以观看视频，
  > 但无法完成任务点」→ 平台级每日上限；触发即停止当日视频任务
- 同项目 `docs/field-notes.md` 2026-09-11 条目（原文逐字）：
  ```
  ### 2026-09-11 — 每日视频任务点完成上限（隐藏提示框）
  - 现象：DOM 中存在隐藏提示框（class `maskDiv jobCountDiv`）：
    「今日视频任务点完成数已达上限，您可以观看视频，但无法完成任务点」
  - 根因：平台级防挂机限制；触发后当天视频不再计进度
  - 解决：触发即停止当日视频任务，整理状态收工，次日续跑
  - 状态：未触发过（预防性知识），持续观察
  ```
  → **关键限定**：作者是"在 DOM 里看到这个隐藏节点"，**自己从未触发过**。
  这解释了为什么它一定是平台内置逻辑（节点由平台代码渲染），但阈值仍然是黑盒。

**② 另一个脚本作者在 FAQ 里直接确认**

- **B｜文档自述**：`DaRin1403/xuexitong-autostudy` README：
  > **Q: 提示"今日视频任务点完成数已达上限"?**
  > A: 学习通平台每日限制(不是脚本限制),今天视频不计分了,明天恢复;学习检测不受影响。

- 该 README 的配置表里，同名功能是**按时长**而不是按个数（注意别抄错口径）：
  > | 每日上限 | 0(不限) | 0 = 不限时长;设正数则刷满该时长自动停止,次日恢复 |

  → 说明社区实现的是"每日**时长**上限"，而我们板块④想要的是"每日**任务点个数**上限"——**两者不是一回事**（见 §7 的裁定理由）。

**③ 我们自己的风险清单里早有这条**

- **B｜二手**：`research/risk-and-tech.md` §0 第 6 条与 §2 表第 10 行：
  > 平台有"每日视频任务点上限"：会出现"今日视频任务点完成数已达上限"的提示，当天不再计分——
  > 这意味着"堆量猛刷"本身会被限额截断。

### 1.2 阈值：**无法确证**（这是本节最重要的一句话）

我把能找到的来源全部检查了一遍，**没有任何一处给出数字**（多少个任务点 / 多少分钟）：

| 来源 | 是否给阈值 | 说明 |
|---|---|---|
| `maskDiv jobCountDiv` 文案 | 否 | 文案只说"已达上限"，不提数值 |
| sans 项目实测记录 | 否 | 明写"未触发过（预防性知识）" |
| DaRin1403 README | 否 | 只给"每日时长上限"配置项（默认 0=不限），FAQ 不提数值 |
| 中南民族大学通知（A，本轮抓原文）| 否 | 全文只有"完整观看""2 倍速上限""90% 才能考试""每天复核"，**无每日上限** |
| 西北师范大学《网络通识课学习注意事项》（A，本轮抓原文 docx）| 否 | 见 §1.3，只有"学习时间偏离正常作息""周期至少一周"，**无每日上限** |
| 桂林理工大学通报（A，本轮抓原文）| 否 | 只有"2000 余条异常数据…视频观看 0 分钟但是完成任务点" |
| `research/risk-and-tech.md` | 否 | 自己就标成 B 级，未给数字 |

→ **结论：阈值是平台黑盒，无法确证。任何默认阈值都是在猜。**

### 1.3 平台侧还是学校侧？

- **倾向平台级**：提示框由平台代码渲染（`maskDiv jobCountDiv` 是平台自己的 class 前缀风格），
  且文案主语是"今日视频任务点"而不是"本课程"。
- **但"阈值是否按学校/课程/账号策略配置"没有任何证据**。同类平台常见做法是"平台能力 + 学校开关"，
  这使得不同学校出现不同上限完全可能——**我们无法排除"某校 30 个、某校无限制"**。
- 级别：**D（推测）**，不要写进代码注释当事实。

### 1.4 本项目同源实测的量级（唯一能当"下限参照"的数据）

**B｜实测记录**：同一知识库 `docs/field-notes.md` 里，有一次通宵连续学习的完整时间线
（课程①《食品营养与食品安全》，30 小节 / 60 任务点）：

| 时间 | 进度 | 累计真实 1x 视频时长 |
|---|---|---|
| 2026-09-16 23:40 | 12/30 小节，24/60 任务点 | ~2h35m |
| 2026-09-17 01:05 | 15/30 小节，30/60（50%）| ~3h15m |
| 2026-09-17 03:20 | 19/30 小节，38/60（63%）| ~4h12m |
| 2026-09-17 05:40 | 22/30 小节，44/60（73%）| ~5h |
| 2026-09-17 06:40 | 23/30 小节，46/60（77%）| — |

同段落原话：「仍无风控迹象」「无验证码、无日上限提示」。

→ **可引用的事实**：这次连续 ~7 小时墙钟、~5 小时视频、累计 44 个任务点的运行里，
**"今日视频任务点完成数已达上限"从未出现**。

→ **但要注意两个削弱因素**（别把它当"阈值 > 44"）：
1. 这 44 个任务点**跨了两个自然日**（23:40→00:00 前约 24 个，之后约 20 个），
   如果上限按自然日结算，单日实际只到 ~24 个；
2. 观察者自己也说"未触发过"，样本 n=1，且换学校/换课程可能不同。

**能做的最强表述**：*「在 n=1 的实测中，单日 ~24 个任务点 / ~5 小时视频量级未触发上限；阈值未知，且可能高于此。」*

## 2. 【问题 2】超限的表现形式

### 2.1 文案原文（用于脚本识别）

- **B｜两处逐字一致**：
  ```
  今日视频任务点完成数已达上限，您可以观看视频，但无法完成任务点
  ```
  （sans knowledge §8 与 field-notes 2026-09-11 完全一致；DaRin FAQ 里用户看到的也是同一句）

**识别建议（可抄）**：
```js
// 容器：平台自己的隐藏提示框
const tip = document.querySelector('.jobCountDiv, .maskDiv.jobCountDiv');
const hit = tip && /今日视频任务点完成数已达上限/.test(tip.textContent || '');
```
- 注意它**默认是隐藏的**（`maskDiv` 家族），所以"存在"不等于"当前生效"——必须同时判可见性
  （`getBoundingClientRect().width > 0` 或 `getComputedStyle(el).display !== 'none'`）。
- 与另一个容易混的弹窗区分：`jobFinishTip` = **单个任务点**未完成（"当前章节还有任务点未完成"），
  `jobCountDiv` = **每日上限**。两者 class 不同（knowledge §8 列出整个 `popDiv` 家族）。

### 2.2 是"播放时拦"还是"提交时拒绝"？

- **都不拦，拦的是结算。** 文案自己写清楚了：「**您可以观看视频，但无法完成任务点**」
  （B，两处逐字）。
- 也就是说：视频能播、进度条能走、`multimedia/log` 心跳照发（推断，D），
  但**任务点不会变绿**，当天白看。
- DaRin1403 的说法与之一致：「今天视频不计分了，明天恢复；**学习检测不受影响**」（B）。
- → 对脚本的含义：**超限是"静默失败"**，不是弹窗阻塞。
  如果我们不主动识别这个提示，表现是"视频一直播、任务点永远不绿"，很容易被误判成
  "我们的完播判定有 bug"，从而反复重播、把账号行为搞得更难看。

### 2.3 第二天怎么恢复

- **B**：只有"明天恢复"（DaRin FAQ）。
- **没有**任何来源说明是「0 点整」「凌晨某刻」还是「上次心跳 + 24h」。
- **D｜推测**：按文案用"今日/明天"的口径，最可能是**自然日（服务器时区，UTC+8）0 点重置**。
- **实现建议**：不要硬编码"0 点"作为唯一判断；更稳的做法是——
  1. 记录"今天已触发上限"这一状态（带日期），当天不再尝试；
  2. 次日首次运行时**先探测一次**：能正常计分（任务点变绿 / 无上限提示）就继续，否则再等。

### 2.4 还有一个"每节一次机会"的相邻机制（容易和日上限混淆）

- **B｜实测记录**（knowledge §15.6）：部分测验附件限制打开次数——「此附件仅支持打开 N 次，
  你已打开 N 次，不能再次打开」，**每节只有一次机会**。
- 这跟"每日任务点上限"是两套东西，但它们在脚本里的处置方式相同：**识别提示 → 停止当前对象 → 记录 → 推进/收工**。

## 3. 【问题 3】分天完成：一门课分几天比较自然

### 3.1 学术证据：arXiv:2609.37280（本轮已抓原文摘要核对）

- **A｜论文原文**（`https://arxiv.org/abs/2609.37280`，2026-09-29 提交）：
  - 标题：*Early Prediction of AI-Assisted Cheating Risk in Online Exams Through Learning Analytics*
  - 摘要关键句（逐字）：
    > The results indicate that LMS interaction data can provide an early signal of AI-assisted cheating risk.
    > **Course-module views, assignment submissions, and the number of days on which course videos were accessed
    > were the most consistently selected features across the LOOCV folds.**
  - 方法/规模：52 名土耳其大一本科生，用**前 8 周**的 LMS 数字痕迹，预测**期末考试**里的 AI 作弊高风险标签；
    5 个特征从 27 个候选里筛出；逻辑回归 Accuracy = **73.1%**。
  - 作者自述边界（逐字）：
    > These predictions are intended to support timely academic guidance, **not to establish misconduct
    > or initiate disciplinary action.**

- **必须说清的三个边界**（否则容易过度引用）：
  1. 它预测的是**考试作弊风险**，标签来自**有监考的线下期末**的考场日志（copy / focus-loss / right-click），
     **不是"刷课"检测**；
  2. 样本只有 52 人、单校单课程，73.1% 准确率；
  3. 「访问视频的天数」是**相关性特征**，不是因果结论，也不是"少于 N 天就算作弊"的阈值。

- **对我们**：它支持一个**方向性判断**——"**在很短时间内集中看完一门课**"会落在异常一侧；
  但**不能**从这篇论文推出"必须分 X 天"。

### 3.2 制度证据（比论文更直接、更可执行）

**① 西北师范大学《网络通识课学习注意事项》（A｜本轮抓到原始 docx 并提取全文）**

原文两条（逐字）：
> 学习进度异常，课程视频观看时长不足，章节测验完成时间过于集中，**学习时间偏离正常作息范围**；

> 网络通识课虽然采取自主学习的形式，但是在安排学习时间时，**尽量避免在凌晨或者偏离正常作息时间范围过大的时间段内学习**，
> 为保证学习质量，**避免在极短时间内完成课程学习（一般情况下，课程学习周期至少控制在一周以上）**，慎重选课，认真学习。

→ **这是本轮找到的、关于"分几天"最硬的一条规则：课程学习周期 ≥ 1 周。**
→ 注意它是"一般情况下"的建议口径，不是硬阈值；但它是学校公文，**写在"合理控制学习进度"条目下**。

**② 中南民族大学通知（A｜本轮抓到原文）**

> 网络课程学习期间，系统每天会对任务点完成情况进行复核。若发现刷课行为，将判定该任务点不通过，需重新自主学习。

→ 与"每天复核"呼应：**判罚是延迟清算**，不是当场拦。这条对"分天"的含义是：
**今天刷完不等于安全，周期过短会在事后被清算**。

**③ 桂林理工大学通报（A｜本轮抓到原文）**

> 近日，超星学习通平台对我校2022级学生的学习数据进行筛查，共发现**2000 余条异常数据**，
> 主要是学生通过不正常手段进行"刷课"（指用脚本或者是**视频观看 0 分钟但是完成任务点**的异常行为）。
> 为严肃教学管理和学习纪律，平台对通过"刷课"获取的学习记录进行了**清除**。

→ 说明平台确实做**批量回溯筛查 + 清除记录**。但它举的异常样本是"0 分钟完成"这种极端情形，
**没有**提"一天看太多"。

**④ 反面证据：三份公文里都**没有**"每日任务点个数上限"**

- SCUEC 通知（本轮抓原文，去标签后约 1.6k 字）：只有"完整观看""≤2 倍速""首次不可拖拽""每天复核""90% 才能考试"。
- NWNU 注意事项全文（24 段）：只有"时长不足""测验时间过于集中""偏离作息""周期≥1 周""多终端""IP 黑名单"。
- GLUT 通报：只有"0 分钟完成"。
→ **"每日 N 个任务点"是平台侧的软机制，不是学校的公开规章**。这进一步支持 §1.3 的判断。

### 3.3 社区/同行经验值

- **B｜DaRin1403 README「安全与合规建议」原文**：
  ```
  1. 倍速保持 1x：挂机就是挂机，让视频真实走完
  2. 每日刷课 ≤ 4 小时，一门课分几天刷完
  3. 正常时段刷课，不要整夜挂机
  4. 刷课时手机 App 退出登录（平台点名"多终端"检测）
  5. 测验偶尔留错题（默认已做），不要门门满分
  6. 考试不碰脚本
  ```
  → 可用的是第 2、3 条：**每日 ≤4 小时 + 分几天 + 不整夜**。但这是作者经验，不是平台规则（B）。

### 3.4 具体到"40 节，分 5 天还是 10 天"

先把量算清楚（按实测均值：上文课程① 22 小节 ≈ 5 小时 → **单节约 13.6 分钟**）：

| 方案 | 每天节数 | 每天视频时长 | 课程周期 | 对照规则 |
|---|---|---|---|---|
| 5 天 | 8 节/天 | ≈ 1h49m | 5 天 | **踩 NWNU「周期至少一周」**（A）|
| 8 天 | 5 节/天 | ≈ 1h08m | 8 天 | 满足 ≥1 周 |
| **10 天** | **4 节/天** | **≈ 54 分钟** | **10 天** | 满足 ≥1 周，且接近"每天一集课"的自然节奏 |
| 16 天（一学期周数）| 2.5 节/天 | ≈ 34 分钟 | 16 天 | 最"像学生"，但很多课有截止日期，未必等得起 |

**裁定：40 节 → 推荐 10 天（4 节/天，≈54 分钟/天）。**

理由（按证据强度排序）：
1. **A**：NWNU 明文「课程学习周期至少控制在一周以上」→ 直接排除 5 天；
2. **B**：DaRin「每日 ≤4 小时、分几天刷完」→ 10 天的每日量（54 分钟）远低于该上限，属于"看不出异常"；
3. **A**（论文，方向性）："访问视频的天数"是被反复选中的风险特征 → 天数多一些、每天少一些，落在更"普通"的一侧；
4. **B**（实测）：单日夜跑 5 小时没触发风控，但那是在**凌晨连续**跑的，**恰恰是 NWNU 点名的异常时段**——
   这不是"可以跑 5 小时"的证据，而是"我们之前的行为正好踩了两个特征"的证据。

**另外一条硬约束**：如果课程有截止日期，10 天排不下时，**优先保"每天少量 + 不熬夜"**，
而不是"压缩到 5 天但每天 2 小时"。因为"周期过短"和"时段异常"都是学校文件里点名的项，
而"每天 2 小时"在文件里**没有任何一条**说不行（见 §4）。

## 4. 【问题 4】单日时长上限 / 连续在线异常

### 4.1 没有"单日 X 小时"的公开上限

- **A**：三份学校公文（SCUEC / NWNU / GLUT）里**都没有**"每日学习时长不得超过 X 小时"这类条款。
  它们管的是**下限与形态**：
  - NWNU：「课程视频观看时长**不足**」→ 不良记录；
  - GLUT：「视频观看 **0 分钟** 但是完成任务点」→ 清除记录；
  - NWNU：「章节测验完成时间**过于集中**」→ 不良记录。
- **B**：`research/risk-and-tech.md` 的风控清单里也没有"日时长上限"这一项，
  只有第 10 项"每日任务点上限"（提示文案级）和第 4 项"异常时长/0 分钟完成"（下限）。

→ **结论：平台公开可见的判定是"太快/太长不看"，不是"看太久"。**

### 4.2 "连续在线 X 小时"会不会触发异常？

- **没有直接证据**。
- 间接相关（B/C）：
  - DaRin FAQ：**长时间挂机会弹人机验证**（滑块 / 微信扫码），"任何脚本都过不了，本人扫码"；
  - `research/risk-and-tech.md` 第 11 项同样记着这条（A/B 混级）。
  - Autovisor（智慧树项目）已知问题：「长时间挂机有概率弹出人机验证，程序检测到后会暂停操作」（B，跨平台类比）。
- **D｜推测**：所谓"连续在线太久"的真实风险路径是
  **长挂机 → 人机验证/掉登录 → 行为序列中断 → 被人工或规则盯上**，
  而不是"服务端有一条 `>X 小时 = 异常` 的规则"。

### 4.3 但有一条**与时长强相关**的真规则：完成周期

- **A**：NWNU「避免在极短时间内完成课程学习（一般情况下，课程学习周期至少控制在一周以上）」。
- 这条等价于：**总时长不变的前提下，把同样的观看量压进更少的自然日 = 更异常**。
  → 这正是板块④要解决的，也是"分天"比"每日时长上限"更重要的原因。

---

## 5. 【问题 5】时段：有没有比 7:00–23:00 更细的证据

### 5.1 只有定性要求，没有钟点

- **A｜NWNU 原文**：
  > 尽量避免在**凌晨**或者**偏离正常作息时间范围过大**的时间段内学习。
- **A｜NWNU 不良记录清单第 2 条**：「学习时间偏离正常作息范围」。
- **没有任何来源**给出"几点到几点算正常"。

→ 我们现有的 `activeHours` 默认 **7:00–23:00** 属于**经验值**（项目自定），
  不是从平台规则推出来的。这点应在 README 里写清，避免读者误以为是平台口径。

### 5.2 可以怎样把"凌晨"落成默认值（有依据的保守选择）

- 「凌晨」在中文语境通常指 **0:00–6:00**（无权威定义，属常识口径，标注 D）。
- 我们的 7:00 起点已经把 0–7 点排除，**比"避免凌晨"更严**，方向正确。
- **建议**：默认保持 `07:00–23:00`，但在文档里明确"这是**保守默认**，依据是 NWNU 的定性要求 +
  常识口径的凌晨定义，不是平台公布的时段表"。
- 可选：给一个"更保守预设" 08:00–22:00（同样无出处，只是更窄）。

### 5.3 一个容易被忽略的点：不要把"时段"和"每日上限"绑死

- 如果用户把 `activeHours` 设成 00:00–24:00（等于关掉），**分天机制仍然应该生效**——
  两者是独立开关。板块④的实现要注意这个组合。

## 6. 实现建议（给板块④的具体接口）

### 6.1 判据与状态

```js
// 1) 上限提示（平台自己的隐藏框，必须判可见）
const dailyCapHit = () => {
  const el = document.querySelector('.jobCountDiv');
  if (!el) return false;
  const visible = el.getBoundingClientRect().width > 0;
  return visible && /今日视频任务点完成数已达上限/.test(el.textContent || '');
};

// 2) 本地计数（脚本自己的软限制，与平台无关）
//    以「任务点完成」（.ans-job-finished / .icon_Completed 出现）为 +1，而不是以「视频 ended」为 +1
//    —— 因为 ended ≠ 平台已记录（见 research/real-video.md §2.2）
```

### 6.2 边界条件（按证据写，不要拍脑袋）

| 条件 | 依据 | 处置 |
|---|---|---|
| 命中平台上限提示 | B（两处逐字文案）| **立刻停当日任务**，写日志「平台日上限，明日再试」，不要重播 |
| 本地计数达到 `dailyTaskLimit` | 我们自己的软限制 | 停当日任务（**与平台无关**，不要写成"已达平台上限"）|
| 跨自然日 | D（无 0 点证据）| 用本地日期字符串做 key 重置；次日**先探测**再继续 |
| 用户手动改系统时间 | — | 不要做防作弊式校验，记录 `lastResetDate` 即可 |
| 中途换课程 | — | 计数**按课程**还是**按账号**？建议**按账号全局**（平台提示是账号级的"今日视频任务点"）|

### 6.3 与"单端纪律 / 拟人化"的关系

- 三者正交：`singleSession`（防多端）、`humanize`（防匀速）、`dailyTaskLimit`（防堆量）。
- 但**都写同一个 sessionStorage key 会互相踩**：建议计数字段独立（`cxas_daily`），
  与 `cxas_epoch` / `cxas_jump_guard` 分开。

## 7. 默认值裁定（必须明确回答的那一节）

### 7.1 结论

> **`dailyTaskLimit` 默认 0（关闭）。**
> 同时提供「推荐开启值」文案与一键预设，**并明确标注"阈值无平台公开依据，以下为基于学校公文与社区经验的保守值"**。

### 7.2 为什么不是"给个保守数字当默认"

1. **阈值无法确证**（§1.2：七类来源全部无数字）。给一个具体默认值（比如 20），
   用户会以为"这是平台的上限"或"这是安全值"，而实际上它只是我们的猜测——
   **错误的确定性比没有默认值更危险**。
2. **平台侧的机制是"静默不计分"**（§2.2），不是"到点弹窗拦住你"。
   如果我们的默认值比平台低，用户会以为"平台不让我学了"，实际是我们自己停的；
   如果比平台高，用户会以为"有保护"，实际早就白播了。两种误解都会让人做出错误决策。
3. **社区同类实现的默认是"不限"**（DaRin1403 配置表：`每日上限 0(不限)`，B）。
   也就是说，**连最强调拟人化的那个项目，默认也不开这个限制**——它的默认值是 0。
4. **本项目当前默认是"关闭一切主动限制"的风格**（`safeMode` 默认开但 `autoSubmitWork` 默认关；
   `humanize` 也是 v2.3 才引入）。突然给一个会**主动停工**的默认值，属行为变更，应显式选择。

### 7.3 但"默认关闭"不等于"不给建议"——推荐值这样给

面板/README 里按课程规模给**预设**（用户点一下才生效）：

| 预设 | 每日任务点 | 每日视频时长（≈）| 依据 |
|---|---|---|---|
| 保守（推荐）| **8–12 个** | 1.5–2.5 小时 | NWNU 周期≥1 周（A）+ DaRin ≤4h（B）+ 实测单日 24 个未触发（B，留一半余量）|
| 温和 | 20 个 | ~4 小时 | DaRin 的 4 小时上限（B），且低于实测 24 |
| 关闭 | 0 | 不限 | 默认 |

> 为什么"保守"取 8–12：40 节 / 10 天 = 4 节/天（§3.4），而一门课通常同时开 2–4 门，
> 合计正好落在 8–16 个/天；取 8–12 既不打断正常进度，也不会出现"一天 40 个"的堆量形态。
> **这是推导值，不是平台规则**——必须在 UI 上这么写。

### 7.4 如果实现者想更简单

那就只做两件事，也能达到 80% 的效果：
1. **识别平台上限提示**（§2.1）→ 命中就停当日、明日再探测。这是唯一有逐字文案支撑的硬信号；
2. **不做本地个数上限**，改为在 README 里给"10 天 / 4 节每天"的分天建议（§3.4）。
   —— 因为"分天"的依据（A 级公文）比"每日个数"（无依据）强得多。

## 8. 未确证 / 不要依赖

| 项 | 状态 |
|---|---|
| 每日任务点上限的**具体数值** | **无法确证**（七类来源无数字）|
| 上限是"个数"还是"时长"（平台内部口径）| 未知；社区实现的是时长（DaRin），平台文案说的是"任务点完成数"（个数）→ **两套口径不一致**，别混用 |
| 上限触发后的**恢复时刻** | 无证据；"明天恢复"是唯一说法。0 点属推测 |
| 上限是否按学校/课程配置 | 无证据（D）|
| "连续在线 X 小时"判定 | **无证据**；已知风险是长挂机弹人机验证（B/C）|
| 正常学习时段的**具体钟点** | 无证据；只有"避免凌晨/偏离作息"（A，定性）|
| arXiv 论文能推出"分 X 天" | **不能**。它是相关性研究、n=52、预测考试作弊风险，作者明确说"不用于认定违规" |
| "一天 40 个任务点一定触发上限" | 无证据；实测 44 个（跨两日）/单日 ~24 个 未触发 |
